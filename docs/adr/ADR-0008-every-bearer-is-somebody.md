# ADR-0008 — Every bearer is somebody: machine tokens and agent connections

Patchy issues two credentials, both owned by a person and each for one door. A **machine token** (`build`) is held by a machine and shared by the agents on it, and lets the CLI act as its person on the API. It expires 90 days after minting or after 30 idle days, whichever comes first. An **agent connection** (`work`) lets an MCP client act as its person at Patchy MCP. Neither opens the other's door, and neither opens a company patch's login door, which admits only Clerk's browser session.

An agent connection is made through OAuth, the protocol MCP clients speak. Patchy is the authorization server; Clerk only signs the person in. A client names itself with a metadata document on its own site, and Patchy keeps no registrations. The person answers on a consent page in their signed-in browser every time, even for a client they've connected before, because any program on their computer can claim a client's id. The answer counts only for the account the page showed. Each consent makes a new connection, since nothing tells two installs of a client apart. The client's code exchange creates the connection, so an abandoned consent creates nothing. A replayed code ends the connection it made.

Access tokens last an hour and are checked against the database on every call, so every ending takes effect on the next call. A rotating refresh token renews them. A retry within a minute gets the same new tokens, the one secret Patchy keeps recoverable, encrypted, for that minute; any later reuse ends the connection. A connection ends after 30 days without a call, however often it refreshes, and has no absolute lifetime: rotation exposes a copied refresh token once both copies are used, and a forced reconnect every quarter would break hosted connectors for nothing.

A device login uses a URL carrying a short code. The person opens that URL in their signed-in browser, checks that the displayed code matches their terminal, names the machine, and confirms or denies. They never type a code into a page: asking someone who did not start a login to relay a code is the phishing path this protocol deliberately avoids. The bare URL explains how to open the terminal's link instead of offering code entry.

Confirmation records authorization, not a credential. The terminal's poll locks the confirmed login, rechecks that its user is active and that their credentials have not ended since the confirmation, mints the token, revokes the previous key only if it belongs to that same user, and deletes the login in one transaction. Plaintext exists only in memory and in the one successful response; only hashes are stored. Concurrent polls have one winner. An abandoned confirmation mints nothing and leaves the old key working. A lost successful response cannot be replayed: the user must start another login rather than recover plaintext from storage.

People control their own credentials on **Your machines**: revoke a machine, disconnect an agent, or disconnect everything, which also cancels device logins and consents that were approved but not yet collected. A machine token is also replaced at its person's next login on that machine and revoked by API logout. Admins have two levers, neither aimed at one credential. Agent access off refuses agents and new connections and cancels consents in progress, but ends no connection. Deactivation ends every one of the person's credentials and pending approvals in one transaction. Reactivation restores none of them.

Disconnect everything and deactivation each record on the person's row when their credentials ended, in their own transaction. Nothing made or approved at or before that time works again: a poll never mints from such a confirmation, and such an agent connection is dead. Reactivation keeps the time, so credentials stay ended whichever release ended them. Dead token rows remain for version provenance and re-login name inheritance. Browser sign-out instead revokes the Clerk session and clears its cookies; it does not log machines out, and remains available before create-or-join and after deactivation.

Every bearer has a human owner. Credentials for unattended CI are a future product decision, not another token kind in this model.
