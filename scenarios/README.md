# Scenarios

What `pnpm dev up <scenario>` builds an environment from. See `docs/DEVELOPMENT.md`, **Environments**.

Each folder holds a `scenario.json`:

- `company`: name and handle, and `agentAccess: true` to start the company's agent access on, turned on by the publisher, so worker agents can use its agent areas from the start. Every start seeds again, but only a company whose switch nobody has touched is turned on, so turning it off at Company lasts until `pnpm dev down`.
- `companies`: optional other companies for outside people, named by handle. The publishing company remains `company`.
- `people`: `key`, `name`, `email` and `admin` or `member` role. An optional `company` handle places the person in another scenario company; omitted means the publishing company. Use `.example` addresses; no mail is ever sent.
- `publisher`: the admin the environment's CLI publishes as.
- `connections`: company connections the publisher makes through their connect page in a browser, as an admin would, before any patch publishes. A Pidgeon connection names its `handle`, `description`, `access` and the new test address's `localPart` and `displayName`; `up` pastes `PIDGEON_TEST_ADMIN_KEY` from the environment or `~/.config/patchy-cloud/dev.env`, adds a code to the local part so each environment's address is its own, and skips the connection without that key. Its optional `mail` names a file beside `scenario.json` with labels and conversations `up` delivers to the new address through Pidgeon's `POST /test/inbound`: customer messages, the desk's replies (`"from": "me"`), sent from the address, `hidden` text Pidgeon's firewall flags, and each conversation's labels and status. Test inbound mail carries no attachments. An Attio connection names its `handle` and `description`; `up` pastes `ATTIO_TEST_READ_KEY`, a read-only key to Patchy's probe workspace, from the environment or `~/.config/patchy-cloud/dev.env`, and skips the connection without it. It only reads, so `down` has nothing to take down in Attio.
- `patches`: repo patches (`repo`, `tier`, `description`, optional `sampleData`, and `connections`, the scenario connections it declares as `integration/handle`, without which `up` skips it and says so) and file patches (`file`, `name`, `description`), published in order.

A repo patch's source is `patches/<repo>/`, holding only builder-owned files: `src/`, `server/`, `agent/`, `helpers/`, `fixtures/`, `index.html`, `patchy.config.ts` and `AGENTS.md`. `up` runs `patchy init` at the scenario's tier, copies these over the starter, refreshes and publishes. Managed files (pins, lockfile, `patchy/_generated/`, project skills) always come from the instance's current release.

`sampleData: true` means the patch's empty state has a **Load sample data** button. `up` presses it once, as the publisher, after publishing. Sample data comes from the patch's own code, so it uses the scenario's people and goes through the patch's own rules.

The rollback rehearsal (`pnpm test:rollback-rehearsal`) seeds `brightline` with the live release, then opens every patch after each upgrade and rollback; a `sampleData` patch fails it if its empty state comes back.

File patches are single-file pages in `files/`, published as tier 1 with their `name` and `description`.

An agent started from the environment's `agent` launcher makes new patches and pages in the workspace beside these repos, as the workspace's `CLAUDE.md` tells it, so `pnpm dev down` removes them with the rest. One builder agent per patch is the norm; nothing enforces it.

A tier 2 repo's `agent/` is its agent area: the tools people's own agents use through Patchy MCP. The environment's worker launchers, `worker-claude` and `worker-codex <person>`, are such agents; DEVELOPMENT's **Environments** says what each needs.
