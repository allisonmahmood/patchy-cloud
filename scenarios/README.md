# Scenarios

What `pnpm dev up <scenario>` builds an environment from. See `docs/DEVELOPMENT.md`, **Environments**.

Each folder holds a `scenario.json`:

- `company`: name and handle, and `agentAccess: true` to start the company's agent access on, turned on by the publisher, so worker agents can use its agent areas from the start. Every start seeds again, but only a company whose switch nobody has touched is turned on, so turning it off in Settings › Agent access lasts until `pnpm dev down`.
- `companies`: other companies, each a name and handle, whose people the company can share a patch with as its guests.
- `people`: `key`, `name`, `email` and `admin` or `member` role, and `company`, one of `companies` by handle, for someone at another company. Use `.example` addresses; no mail is ever sent. `deactivated: true` deactivates them once `up` has published what they own; reactivating them at People lasts until `down`. `computers` (`name`, `used`) and `apps` (`name`, `site`, `connected`, optional `used`) are what Your agents lists for them, as display-only rows: a computer unused for 30 days, or an app 30 days without a call, has ended.
- `publisher`: an admin of the scenario's own company, whom the environment's CLI publishes as.
- `invitations`: `email`, `role` and `sent`, invitations the publisher sent, recorded as mailed unless `unsent: true`; one sent 30 days ago has expired.
- `connections`: company connections. One with a `state` is offline: `up` writes it straight into the database, as connect saves one, with invented credentials sealed by the instance's own keys and an invented snapshot, so nothing reaches its integration and no key is needed. It is saved connected before any patch publishes, then left `connected`, `paused` (disconnected by the publisher) or `needs-attention` for its integration's own reason: an Attio key a Test found writable, an IMAP login the mail server refused, a Pidgeon key Patchy replaced but couldn't revoke. Postgres and PostHog keep no such reason. An offline Pidgeon connection may say `test: true`, and any may say `blockGuests: true`. Test, Resume or Replace on one sends its invented credentials to the integration, which refuses them. The rest are live: the publisher makes them through their connect page in a browser, as an admin would, before any patch publishes. A Pidgeon connection names its `handle`, `description`, `access` and the new test address's `localPart` and `displayName`; `up` pastes `PIDGEON_TEST_ADMIN_KEY` from the environment or `~/.config/patchy-cloud/dev.env`, adds a code to the local part so each environment's address is its own, and skips the connection without that key. Its optional `mail` names a file beside `scenario.json` with labels and conversations `up` delivers to the new address through Pidgeon's `POST /test/inbound`: customer messages, the desk's replies (`"from": "me"`), sent from the address, `hidden` text Pidgeon's firewall flags, and each conversation's labels and status. Test inbound mail carries no attachments. An Attio connection names its `handle` and `description`; `up` pastes `ATTIO_TEST_READ_KEY`, a read-only key to Patchy's probe workspace, from the environment or `~/.config/patchy-cloud/dev.env`, and skips the connection without it. It only reads, so `down` has nothing to take down in Attio. An IMAP connection names its `handle`, `description` and the mailbox's `username`; `up` starts a Dovecot mailbox in Docker for the environment at `mail.<company handle>.test`, signed by a CA of the environment's own, connects it through the connect page, and skips the connection when Docker isn't answering. Its optional `mail` names a file beside `scenario.json` with `folders` and `messages` (`folder`, `from`, `subject`, `date`, `text`, optional `seen` and one `attachment` with its `filename`, `contentType` and `text`) that `up` puts in the new mailbox over IMAP, once. `down` removes the mailbox.
- `patches`: repo patches (`repo`, `tier`, `description`, optional `sampleData`, and `connections`, the scenario connections it declares as `integration/handle`, without which `up` skips it and says so) and file patches (`file`, `name`, `description`), published in order. Either kind may name `guests`, people at other companies than its owner's by key, whom `up` shares it with through the CLI (`patchy share --add`), so a guest's view needs no manual step. Either may also say:
  - `from`: another scenario whose source it publishes, from that scenario's `patches/` or `files/`.
  - `owner`: whose patch it is, by key; `up` publishes, shares, retires and deletes it with a machine token of theirs that ends once `up` is done. The publisher when absent.
  - `versions`: how many times `up` publishes it, each a new version.
  - `age` and `updated`: how long ago its first and latest versions were published, such as `"30 days"`; the rest are spread between them. Both are just now when absent.
  - `opens`: how often each person, by key, has opened it, for Home's Your usual, New and Popular.
  - `retired` or `deleted`: how long ago its owner retired or deleted it.
  - `calls`, on a tier 2 repo: entries for its log, each `by` a person, optionally `via` an app, naming its `handler` and `kind`, an `outcome` of `succeeded`, `failed`, `refused`, `running` or `unknown`, a failure's `reason`, optionally the declared `connection` it went through (`name`, `op`, `resource`), and how long `ago`. A failed or refused one in the last day counts as a failure today; a running one reads Running until its deadline, an hour after it began, then Unknown.
  - `reads`, on a tier 2 repo: shared tables of earlier repos of its company's, as `patch` and `table`, which `up` declares with `patchy add shared-table`.

  `up` makes the history true after publishing, writing the dates, opens and log entries straight into the database.

A repo patch's source is `patches/<repo>/`, holding only builder-owned files: `src/`, `server/`, `agent/`, `helpers/`, `fixtures/`, `index.html`, `patchy.config.ts` and `AGENTS.md`. `up` runs `patchy init` at the scenario's tier, copies these over the starter, refreshes and publishes. Managed files (pins, lockfile, `patchy/_generated/`, project skills) always come from the instance's current release.

`sampleData: true` means the patch's empty state has a **Load sample data** button. `up` presses it once, as the publisher, after publishing. Sample data comes from the patch's own code, so it uses the scenario's people and goes through the patch's own rules.

The rollback rehearsal (`pnpm test:rollback-rehearsal`) seeds `brightline` with the live release, then opens every patch after each upgrade and rollback; a `sampleData` patch fails it if its empty state comes back.

File patches are single-file pages in `files/`, published as tier 1 with their `name` and `description`.

`pnpm dev eval` stages the scenario of a task that changes an existing patch the same way, into each run's own company through that run's sandboxed CLI, keeping the instance's own `AGENTS.md`. Connections can't be staged yet, so a scenario its tasks use declares none.

An agent started from the environment's `agent` launcher makes new patches and pages in the workspace beside these repos, as the workspace's `CLAUDE.md` tells it, so `pnpm dev down` removes them with the rest. One builder agent per patch is the norm; nothing enforces it.

A tier 2 repo's `agent/` is its agent area: the tools people's own agents use through Patchy MCP. The environment's worker launchers, `worker-claude` and `worker-codex <person>`, are such agents; DEVELOPMENT's **Environments** says what each needs.
