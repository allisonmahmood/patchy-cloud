Does a dozen tokens and a brief make a tool look like its company?

Four looks were captured and fresh agents built the same small tool in each of them. Every tool built in a look was then restarted under every other look with no code change, and two more agents changed a tool after its look was revised. This page shows all of it side by side.

What to judge. For each of the four rows below, does the tool on the right read as the company on the left?

The agents were never told about the look. Each got the same prompt for a tier 1 spend-request tracker, in a repo where generation had laid down look.css, the logo and a patchy-look skill holding the brief. The look capture used fallback font stacks and a placeholder logo, because brand fonts and logos can't go into the public repo. Screenshots were taken on Linux, the worst case for fallback fonts.

Proposed verdict (Allison decides)

  1. Fifteen tokens: the 13 plus --look-success and --look-warning. Colour tokens are opaque #RRGGBB.
    • Status colours were the one gap every capture and three of the four tools hit, and the only thing that broke in a re-skin.
    • Pending is neutral, shown in fg or muted, not warning.
    • --look-link stays: all four looks set it apart from the accent.
  2. Tighter definitions, since the names are a permanent contract:
    • --look-accent: the principal brand emphasis fill. Text on it uses --look-accent-fg. It doesn't mean the primary button, selection or status; three of the four brands don't fill their primary button with it. A plain button is the look's call.
    • --look-space: the reference layout gap, nominally 8px, not the smallest grid step. A label gap is half of it, related controls one, panel padding three. Linear's 4px made re-skins change density by about 50%.
    • --look-surface: an alternate ground that carries the same foregrounds as bg.
    • --look-border: decorative separators and frames. Control outlines are the look's call.
  3. One contrast rule. Every foreground (fg, muted, link, danger, success, warning) reaches 4.5:1 on both bg and surface, and accent-fg reaches it on accent. Today's looks would need three small fixes: Duolingo's danger (4.30) and muted on surface (4.24), and Vanguard's muted on surface (4.21).
  4. Not added:
    • a mono font, a second radius, a border width, surface levels, a danger foreground, type-scale tokens;
    • a dark variant. One look is one colour scheme, and color-scheme may sit in :root.

    Recipes carry literals for sizes, weights, shadows and pills.

  5. The brief keeps its nine sections, and recipes ship markup with their CSS. One agent had to rebuild the tabs recipe on buttons because it styled links. Components must include a badge per status (neutral too), tabs or a segmented filter, a select and a small button. The reference allows pseudo-classes in element styles, and literal sizes.
  6. The specimen keeps its current contents and adds a badge per status, plus focus, hover, invalid, disabled and busy states. It checks look.css and the tokens, not the brief's recipes, and it says so.
  7. Size cap: the folder is at most 512 KiB of published bytes, embedded fonts included. LOOK.md is at most 32 KiB.
  8. "No company look" stays a state. Generation writes the Patchy look as Patchy's default, with no company logo and never as a company revision. look restore none returns to it.
  9. A new revision recolours existing tools; it doesn't restructure them. In the revision runs, an agent extending the Linear tool under Duolingo's look kept the tool's own style, as the precedence rule says. An agent told "update this tool to our current look" rebuilt it in Duolingo's style in under 4 minutes. Change notices say this, and the way to match a new look is that one line, pasted to the owner's agent.
  10. Plain-element styles carry no signature effects. Duolingo's plain button (lip shadow, press transform, uppercase) leaked into the Linear tool's own tab and ghost buttons after the revision, and the agent had to reset it. In look.css, element styles set colours, fonts, borders, radius and spacing only. Shadows, transforms, text-transform and letter-spacing go in the brief's recipes, which patches copy and own.

What the build tickets still have to test

From Astra's review of this prototype (GPT-6 Astra, a different model family). None of these needed another prototype round; each belongs to the ticket named.

  • #565 revisions and checks: conflicting token declarations, transparent colours, and !important breaking the override promise. Check the effective values, not just that each token is present.
  • #566 preview: keyboard use, narrow screens, zoom, long labels and non-Latin text, plus the same tool compared across two revisions.
  • #567 generation: the Patchy look, then a company look, a restored revision and none, in that order. Also interrupted generation, an existing styled repo and real tier 0 font publishing.
  • #568 change notices: a brief-only revision, then an agent extending an existing patch. The notice says the look changed and existing components were not restyled.
  • #569 onboarding: ambiguous email domains, product pages behind a login, and an owner who rejects a faithful capture of their marketing site.

Also found

  • The dev environment's agent isn't fresh. pnpm dev up puts the agent workspace under $HOME, so Claude Code loads ~/.claude/CLAUDE.md as an ancestor file even with --setting-sources project. These runs used a workspace under /tmp.
  • Agents read the global skill from node_modules. With no look, the agent found patchy/skills/patchy/references/patchy-plan-style.md in the installed package and followed it. Retiring style.md (#569) should account for that path.
  • A plain button as the primary button works, but every other button needs a recipe class, and one agent had to reset the primary style on its filter buttons.
