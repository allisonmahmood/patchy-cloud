# `patchy init --tier 2` to a published two-artifact version (prototype)

Throwaway vertical slice for [#314](https://github.com/allisonmahmood/patchy-cloud/issues/314) on the tier 2 map (#294). Never merged. Every new or changed file carries a `PROTOTYPE for #314` comment; `git grep "PROTOTYPE for #314"` is the blast radius.

## Try it

From the worktree, with the Clerk development keys loaded as `docs/DEVELOPMENT.md` says (or a dotenv with an offline `CLERK_JWT_KEY`, which is what the smoke used):

```sh
pnpm install
pnpm dev                                   # builds the patchy tarball, starts Postgres + server + one workerd
set -a; . .local/dev/env; set +a
mkdir -p /tmp/t2 && cd /tmp/t2
node <worktree>/packages/patchy/dist/index.js init notes --tier 2 --purpose "Team notes" --json
cd notes && pnpm exec tsc --noEmit         # the scaffold typechecks
node <worktree>/packages/patchy/dist/index.js dev --json   # url (owner) and colleagueUrl (fixture colleague)
node <worktree>/packages/patchy/dist/index.js publish --json
```

Open the published address in a signed-in browser: the page lists notes through `patchy.server.notes.list()` and adds one through `patchy.server.notes.add({ title })`; an empty title comes back as the handler's `empty_title` error. Add `import { z } from "zod"` to `server/notes.ts` (with `zod` installed so `tsc` passes) and publish again to see the import check refuse. `pnpm dev stop` and `patchy dev stop` clean up.

In round 1 a mutation's writes were not atomic across callbacks (`writeThenThrow` left its row). Round 2 holds one company transaction per invocation host-side; see `## Round 2`. The skill's sentence about atomicity is updated there.

## Design notes for the map

- **Errors do not cross workerd RPC with their properties.** The loader's `Callbacks` stub threw an `Error` with a `patchyRefusal` field; the guest received a bare `Error`, so a refused write from a query surfaced as `handler_failed`. Fixed by returning refusals as data and rethrowing in the guest entry. #298's "the guest holds an RPC stub" should say the stub answers with a result, not a throw.
- **A handler error is a successful reply**, so the `runtime_calls` row for `empty_title` says `outcome = success`. Decide whether handler errors get their own outcome or ride as success with a code.
- **The generated client needs the `server/` file list**, so adding a file needs `patchy refresh`; a changed export or schema does not (type-only import). #296 point 10 says "no regeneration step"; it holds for edits, not for new files.
- **`optional` on an argument field means the key may be omitted; null needs `t.nullable`.** On table columns `optional` means nullable. Two meanings for one word; the skill states it.
- **Discovery re-derives on the exact stored bytes** (a throwaway workerd per publish, ~45 ms; 5 s bound); the comparison is order-independent JSON. The disagreement message lists handler names only, so a kind or shape mismatch with identical names reads oddly.
- **Two dev identities are two listeners**, because the broker posts to a fixed `/api/runtime/call` and a base path cannot select a principal without a browser-supplied field. The listener is the mount.
- **Vite 8 library mode is enough for the server bundle** (`rolldownOptions.output.codeSplitting = false`); Vite's own `vite/modulepreload-polyfill` import is allowlisted, or `build.modulePreload: false` in the scaffold would remove it.
- **workerd pinned at 1.20260924.1** (a day older than the spike's), so pnpm's `minimumReleaseAge` needed no exclusion; its postinstall is off and the platform package's binary is spawned directly. The patch repo installs it as a devDependency with `--ignore-scripts`.
- **The engine in the server is one process per server**; a rebuilt version is a new worker name (`patch@version#digest`), the bundle is pushed on `bundle_required`.

### 2. One company transaction per mutation across callbacks

- `packages/execution/src/Transaction.ts` (new): a mutation opens one company transaction **at admission** (simpler than on first callback, and the gap between admission and the first callback is a held connection, not a correctness risk) on its own fiber: `BEGIN` through the existing `withCompany` + `withTransaction`, then `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`; a query gets `REPEATABLE READ READ ONLY`, an action the serialised fiber with no transaction. Every callback is a job on that fiber, so callbacks serialise on the transaction and the table handlers' own `withTransaction` becomes a savepoint on the same connection (a `unique_violation` rolls back its savepoint, the invocation continues). Completion joins the running job, drains and refuses the rest, shuts the queue (a callback that had already been parsed is refused, never run against a closed transaction), then commits only when the driver says commit, which `ServerCall` says only after the handler returned and the result validated; a handler error, an invalid result, `handler_failed`, the deadline and a process loss all roll back.
- A 40001 anywhere (at a statement inside a callback, where the table handler had mapped it to a refusal, or at commit) re-invokes the whole handler, mutations only, up to three attempts, each `engine.invoke` minting a fresh capability so a late callback from attempt one is refused. On PGlite `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` is accepted; PGlite is one connection, so concurrent transactions serialise behind its acquirer and 40001 never occurs there.
- Bound: two concurrent invocations per company, `busy` fail-fast past that. The company pool has four connections; an invocation's transaction holds one for its life and each callback borrows a second through the table handlers' own `withCompany`, so four slots carry two invocations. A build folds the callback's borrow into the held connection and gets the full four.
- Measured on the instance's Postgres: **`writeThenThrow` leaves 0 rows** (three runs); ten-callback mutation **p50 14 ms server-side** (12-24; 18 ms wall incl. curl); `writeThenTimeout` (insert, then sleep past the deadline): `handler_timeout` at 10.01 s and **0 rows** (rollback confirmed); eight concurrent `bump`s on one counter row with the client retrying `busy`: **total 8, one row, 3 serialization retries, 12 `busy` refusals, 462 ms wall**. On PGlite (`patchy dev`): `writeThenThrow` 0 rows, ten-callback **p50 22 ms wall**, paired concurrent bumps 1→8 in order with no retries and no `busy`, `writeThenTimeout` 0 rows.
- Skill: `patchy-server` now says a mutation's callbacks share one transaction that commits after the handler returns and the result validates, and that a 40001 re-runs the handler, so mutations must be safe to run twice.

### 3. Astra's code points

- `t.row("<table>")` validates the declared row shape from the pinned manifest: system columns, every column's kind, optionality, no unknown keys (`probe.fakeRow` → `handler_failed`, log `$.createdAt: expected an ISO timestamp`; real rows from `notes.list` pass).
- Descriptor grammar is closed: a descriptor carries only its own keys, a handler descriptor only `kind/args/result/errors`.
- `ServerCall` never casts a guest-reported refusal code: the host keeps the refusal it issued in the callback closure and answers with that (status and details intact); anything else the guest reports is `handler_failed`.
- Discovery disagreement names the path: `notes.add.kind: declared "query", bundle says "mutation"`, `notes.list: not declared, bundle has it`.

### 4. Watchdog (stretch)

- When an invocation times out the engine records it as overrun; every 250 ms the watchdog probes the serving workerd's `/healthz` (500 ms) while anything is overrun; a spinning isolate blocks workerd's one thread, so an unanswered probe after a 1 s margin is the evidence, and the process is `SIGKILL`ed and respawned. In-flight invocations of that process fail as `ProcessKilled`; `ServerCall` rolls their transaction back and reports `handler_timeout` (a confirmed non-commit), never `unknown_outcome`, which stays reserved for a commit whose reply was lost. Bundles are pushed again on the next `bundle_required`.
- Measured: `probe.spin` (`for(;;){}` inside a handler) → `handler_timeout` at 10.03 s; a `probe.whoami` sent 1 s later blocked behind it and hit its own deadline at 10.01 s (its own timeout came before the kill, so the `ProcessKilled` classification was not the path it took); the process was replaced 18 ms after the kill decision (kill to healthy replacement); `notes.list` answered 23 ms later; exactly one workerd alive afterwards. This is execution compatibility with production's loader and binary, not Fargate containment: no RSS bound, no per-process isolation, one process per instance.

## Round 3 (2026-09-25, same laptop)

Steps 1 and 2 were built by the previous round 3 builder (commits `9548a9e`, `7ebeb9c`); their numbers below were re-measured by the builder who finished the round. Every run is on the worktree's `pnpm dev` instance (embedded Postgres 18, one company) unless it says PGlite.

### 1. The enforcement fences (astra's second pass)

- **Liveness and settlement.** The callback listener parses the body, then checks the capability is still live. Completion revokes admission, joins the running callback, refuses every queued one, then finalises. The transaction fiber's readiness (`BEGIN`, isolation, `SET LOCAL statement_timeout`) is awaited before admission completes, and queued jobs are refused on every fiber exit, interruption included.
- **Abort-only.** A 40001 anywhere in the attempt (a statement inside a callback, commit, or one the guest caught) marks it abort-only. After that the guest's return value decides nothing: callbacks settle, the attempt rolls back, and a mutation is re-invoked, up to three attempts.
- **Outcome from the commit phase.** The transaction is verified with a `SELECT 1` before `COMMIT`, because an aborted transaction answers `COMMIT` with a rollback and no error. `unknown_outcome` is only a `COMMIT` that was sent and whose reply failed. A failure before that is a confirmed rollback (`handler_timeout` or `handler_failed`).
- **One pool slot per invocation.** `Transaction.joiningDatabases` wraps `CompanyDatabases.withCompany` so a callback on the transaction fiber reuses the held connection. It lives in the execution seam, and the primitives are unchanged. The table handlers used for callbacks are built over it in `apps/server/src/Server.ts` and `packages/patchy/src/devResources.ts`, so the company's four connections carry four invocations and the fifth gets `busy`.
- **One deadline** spans admission, every attempt and settlement. `SET LOCAL statement_timeout` is the remaining deadline, so a statement in flight is cancelled at the deadline.
- **Also closed:** descriptor lookup uses own keys; undeclared handler error codes are `handler_failed`; refusals the guest reports are checked against the refusals the host issued to that invocation; `t.row` requires every column; the `vite/modulepreload-polyfill` exemption is gone.

### 4. A subscription on a tier 2 query

- **Client:** `patchy.server.<module>.<query>.subscribe(args, onSnapshot, { onError, onStatus })` returns an unsubscribe. It lives on the framework-free core client, typed only on query handlers (`QueryClient` in `patchy/server`); nothing was added to `patchy/preact`. The registry is #313's: one live subscription per handler and canonical arguments, refcounted, a one-second grace before the last unsubscribe ends it, and a per-subscription revision that drops stale snapshots. A handler error in a re-run reaches `onError` and the last good value stays.
- **Shell:** the broker's subscription stream is lifted from #313 (PR #343): one fetch-streamed SSE stream per document, forwarded to the frame. The one change is that `server.call` is admitted as a subscribable op even though its kind is `mutation`, for the Origin check.
- **Server:** `packages/runtime/src/SubscriptionStream.ts` (#313's stream routes) re-runs a subscription through `Runtime.call` under the stream's own request, so each re-run is re-admitted as the subscriber, on the query's `REPEATABLE READ READ ONLY` snapshot. It delivers the whole reply only when it changed.
- **Dependencies are traced per run.** ServerCall's callback host adds each callback's table key (`table:<patch>/<name>`, a shared alias resolved to the owner's table from the pinned manifest) while the stream's `Invalidation.Subscribed` reference is set. The query's dependencies are therefore what its last run read, never a declaration. With the reference set, ServerCall refuses anything but a query.
- **Wakes:** `packages/runtime/src/Invalidation.ts` is an in-process key bus. A tier 2 mutation wakes after its own `COMMIT` in ServerCall, with the tables its callbacks wrote. A tier 1 table write wakes from `Runtime.dispatch`, which is #313's hook. The dev loop wakes `version:<patch>` when it rebinds a bundle. A wake that lands while a run is in flight is kept and checked against the run's new dependencies, because a first run's dependencies are unknown until it returns.
- **Coalescing:** #313's 25 ms trailing debounce with a 250 ms ceiling and one re-run in flight per subscription. Re-runs share a process-wide concurrency of 4 and retry `busy` with backoff.

### Round 3 design notes for the map

- **Dependency tracing costs nothing extra in the callback seam.** The callback host already sees every table operation under its binding, so table-grain dependencies are one set insert per callback and need no cooperation from the guest. #297's "tables the run touched" holds as decided. Shared aliases resolve to the owner's key from the pinned manifest.
- **A wake during a run must be kept.** With traced dependencies, a first run does not know its keys until it returns, so a commit that lands mid-run would be dropped if it were matched against the old set. #313's static key never had this case.
- **`server.call` is a mutation on the wire**, for the Origin check, so subscribing a query needed a broker exception, and "only a query" is enforced by ServerCall per run through a context reference. A build could give queries their own wire kind, or a `server.subscribe` op.
- **The limits ticket should bound waiting, not only admission.** A bare `busy` makes clients retry through full admission, and at 20 viewers that retry traffic cost half the throughput. A short bounded queue at the company slot, or exponential client backoff, belongs in #304.
- **Serialization exhaustion needs its own code.** Hot-row mutations exhaust three attempts at four-way concurrency, and `source_unavailable` reads as an outage. It needs a retryable `conflict` (or `busy`), or more attempts with jitter.
- **The server process, not the pool, is the throughput bound** at about 3 ms of server CPU per call. The pool size moves p50 more than it moves throughput.
- **workerd RSS needs a bound in #298's supervisor**, because one long-lived isolate grows under sustained load.
